Date : 2026-11-16. Branche : feat/phase-11-admin-1 (rien de commité, comme demandé).

## Ce qui est fait
- Adresse secrète : `ADMIN_PATH` (serveur seulement), validée par Zod dans `src/server/env.ts` (8 à 64 caractères, lettres, chiffres, `-`, `_`, mots réservés refusés, vide = admin fermé) ; ajoutée à `.env.example` ; tout `NEXT_PUBLIC_*ADMIN*` est refusé.
- `src/server/auth/admin-path.ts` : `isAdminSegment` (sensible à la casse, tout refusé sans `ADMIN_PATH`).
- `src/server/auth/admin-session.ts` : `ADMIN_SESSION_HOURS = 12`, `isAdminSessionExpired`.
- `src/server/auth/require-admin.ts` : `requireAdmin` (404 pour non-admin, 401 `MFA_REQUIRED` pour admin aal1 avec appareil, 404 si aucun appareil) et `requireAdminUser` (admin sans exiger le code, pour la connexion et l'enrôlement).
- `src/server/admin/mfa.ts` : `mfaSetupStatus` (2 appareils TOTP vérifiés), vérification du code sur chaque appareil, enrôlement, alerte `admin_login_failed` tous les 5 mauvais codes (sans le code ni l'email).
- Routes : `POST /api/v1/admin/mfa/verify` (demandée), plus `GET /api/v1/admin/mfa/status` et `POST/PUT /api/v1/admin/mfa/enroll` (nécessaires pour enregistrer les 2 appareils, absentes d'`API_SPEC §8`).
- Page de connexion cachée : `src/app/gestion/[adminPath]/` (layout 404 si segment faux, `noindex, nofollow` en balise et en-tête, sous-adresses provisoirement 404), composants `src/components/admin/`.
- `src/proxy.ts` : réécrit `/<ADMIN_PATH>` vers `/gestion/<ADMIN_PATH>` ; tout le reste (dont `/admin`) suit le chemin normal et finit en 404.
- Signal « même IP » : `registerUser` enregistre `hashIp(ip)` dans `profiles.signup_ip_hash` (jamais l'IP ; pas d'enregistrement si IP inconnue ; une panne n'empêche pas l'inscription). Test : `tests/unit/auth/register-ip-hash.test.ts` (nouveau fichier).
- Textes FR/EN dans `src/messages/admin.fr.json` et `admin.en.json` (fichiers séparés : `fr.json` et `en.json` sont modifiés en même temps par un autre coder).

## Choix et écarts
- Le dossier `src/app/[adminPath]` du LLD est impossible : Next refuse deux segments dynamiques différents à la racine à côté de `[locale]`. J'ai donc mis `src/app/gestion/[adminPath]` et un rewrite dans le proxy. Le LLD §2 est à mettre à jour (docs : hors de mon périmètre).
- La connexion par mot de passe réutilise `/api/v1/auth/login` (avec Turnstile). Les échecs de mot de passe ne déclenchent donc pas `admin_login_failed` ; seuls les mauvais codes à 6 chiffres le font. Si le propriétaire veut aussi les mots de passe, il faut une route de connexion admin dédiée (à décider).
- Compteur d'échecs : table `login_attempts` (hash du compte admin), fenêtre 15 min, alerte à 5, 10, 15…
- `src/server/providers/telegram.ts` : une ligne ajoutée (événement). Le coder C peut aussi y toucher : vérifier la fusion.
- Test ajouté dans `tests/` alors que ma fiche l'interdit : demandé explicitement par le chef de projet pour `signup_ip_hash`.

## Points pour lp-security
1. Enrôlement du 1er appareil : mot de passe seul suffit (Supabase). Tant que l'admin n'a aucun appareil, quelqu'un qui connaît le mot de passe pourrait enregistrer le sien. À faire tout de suite à la mise en place (11.5) ; confirmer que Supabase exige bien aal2 pour le 2e appareil.
2. Mauvais code : Supabase limite aussi de son côté ; notre alerte ne bloque pas (pas de verrouillage au-delà de la limite Supabase).
3. `last_sign_in_at` sert de contrôle 12 h en plus du `timebox` de la config.
4. Le segment secret est transmis à la page de connexion (props) pour rediriger après succès ; il est déjà connu du visiteur à ce stade.
5. `requireAdmin` renvoie 404 pour un admin sans aucun appareil, mais `MFA_REQUIRED` révèle qu'une route existe à un admin déjà connecté (voulu par la spec).
6. Le proxy lit `process.env.ADMIN_PATH` directement (pas `env.ts`) ; si la valeur est invalide, le layout échoue à la validation.
