## Partie 1 — les 4 tests rouges

a. `admin-stats` (totaux doublés, test instable) — **le TEST était faux.** Les tests de base ne sont pas annulés : les commandes, recharges et profils laissés par les passages précédents restent. La date de test était tirée au hasard parmi 800 années ; avec des milliers de passages, la même année ressort souvent et les totaux se doublent. Correctif : nouvelle aide `freeWindowNow()` (`tests/helpers/admin-db.ts`) qui tire une date, vérifie que les 41 jours avant sont vides (commandes, paiements, profils) et en retire une autre sinon. Résultat : 23/23 verts sur 3 passages de suite. Code serveur intact.

b. `admin-users` « caractères spéciaux "_" » — **le CODE est faux** (le test aussi était mal fait, mais ce n'est pas la cause). Le test cherchait `_` seul : il pouvait trouver de vrais clients de la base locale. Je l'ai rendu déterministe : il crée son client (`<mot>-0@lyonpanel.test`) puis cherche `<mot>` + caractère spécial + `0@lyonpanel.test`. Un joker (`%`, `_`, `*`) retrouverait le client ; un texte simple ne le trouve pas. Résultat : seul `_` reste rouge, `%`, `*`, `,`, `)`, `'`, `\` passent. **Défaut dans `src/server/admin/users.ts` ligne 25** : `q.replace(/_/g, '\_')` — en JavaScript, `'\_'` vaut `'_'` (le antislash disparaît), donc rien n'est échappé. Il faut `'\\_'`. Non réparé (hors de mon périmètre) : pour lp-coder.

c. `schema.test.ts` « refuse un solde négatif » — **le CODE (la migration) est faux.** Le test existait avant la phase 11 et doit continuer à passer. La contrainte écrite est `check (balance_xaf >= 0 or current_setting('lyonpanel.allow_debt', true) = 'on')`. Tant que le réglage `lyonpanel.allow_debt` n'a jamais été posé dans la connexion, `current_setting(..., true)` renvoie **NULL** ; `faux OR NULL` = NULL, et une contrainte CHECK qui donne NULL est **acceptée**. Le solde négatif est donc accepté par une écriture directe (sur une connexion qui n'a pas encore appelé `cancel_referral_bonus`), ce qui ouvre exactement la porte « modifier un solde avec un simple update » que le CLAUDE.md interdit. Le test est rouge à juste titre. Correctif à demander à lp-db (je n'y touche pas) : `coalesce(current_setting('lyonpanel.allow_debt', true), '') = 'on'`, pour les deux contraintes (`wallets_balance_xaf_check` et `wallet_transactions_balance_after_xaf_check`, même schéma).

d. `tickets-purge-orphans` « confirm = undefined » — **le TEST était faux.** `purge(paths, confirm = true)` transformait `undefined` en `true`. Correctif : `purge` prend maintenant des paramètres rest ; `confirm` ne vaut `true` que si l'appel ne le précise pas, et un `undefined` explicite arrive tel quel au service. Résultat : vert.

## Contrat à confirmer (hypothèses que j'ai dû faire)
1. **Adresse secrète transmise par le navigateur** : la page `/<ADMIN_PATH>` envoie `admin_path` dans le corps ; le service la compare à `ADMIN_PATH` (`isAdminSegment`). Sans cela l'API ne peut pas savoir si le visiteur connaît l'adresse.
2. **Limiteur de tentatives et alerte à 5** : le vrai limiteur bloque dès le 4e échec sur un même identifiant (AUTH_LOCKED, pause 15 min), donc l'alerte « tous les 5 échecs » ne serait jamais atteinte avec un seul identifiant. Mes tests isolent l'alerte (limiteur neutre). lp-coder doit compter les échecs de la route admin à part (clé fixe `admin-login`, table `login_attempts`, avant la vérification du limiteur), sinon l'alerte reste inutile. À trancher : l'alerte compte-t-elle tous les échecs sur cette route ou seulement ceux de l'email de l'admin ? J'ai écrit la première lecture, la seule qui ne révèle pas quel email est celui de l'admin.
3. **`signOut` pour un client ordinaire** : un compte non admin avec un bon mot de passe reçoit la même réponse que pour un compte inconnu, mais Supabase aura ouvert sa session : le service doit la fermer.
