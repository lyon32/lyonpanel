# Tâche 12.3D : pagination de GET /admin/services + enquête name_fr / name_en

## Pagination
- `GET /api/v1/admin/services?platform=&active=&q=&page=&limit=` : page (défaut 1), limit (défaut 50, max 200), ordre stable sort_order puis id.
- `q` : nom FR/EN (ilike, caractères spéciaux du filtre retirés) ou identifiant exact si numérique.
- Réponse : `{ items, total, page, limit, hasMore }`. Coût et nom fournisseur restent admin seulement.
- Fichiers : src/server/schemas/admin-services.ts, src/server/admin/services.ts, API_SPEC.md (ligne §8).
- Test modifié : tests/db/admin-services.test.ts, seule la requête change (ajout de `q=<id du service créé>&limit=200`) ; les vérifications (coût, marge, prix) sont intactes.
- Résultat : admin-services 18/18 verts ; lint 0 erreur (14 warnings existants) ; typecheck OK.

## Enquête name_fr / name_en (aucune modification)
- Lecture de `name_fr` : vue `services_public` -> public-catalog.ts, order/page.tsx ; place-order.ts (nom dans la commande) ; admin/orders.ts. list-orders.ts et suggest-order.ts s'en servent seulement en repli quand `category` est vide.
- `name_en` n'est lu nulle part côté client (colonne ajoutée à la vue mais jamais consommée).
- Le catalogue client affiche des noms générés par `buildServiceName(service, locale)` (src/server/catalog/build-name.ts), via present-catalog.ts, list-orders.ts, suggest-order.ts. `name_fr` n'est écrit que par la synchro (même fonction buildServiceName), jamais depuis le nom fournisseur.
- Conclusion : renommer dans l'admin n'a aujourd'hui AUCUN effet visible côté client.

## Proposition (non implémentée)
1. Dans `buildServiceName` (ou juste son appelant dans present-catalog / list-orders / suggest-order) : si la ligne a un `name_fr`/`name_en` posé par l'admin, l'utiliser selon la locale, sinon le nom généré.
2. Problème : `name_fr` contient déjà le nom généré par la synchro, donc impossible de distinguer un renommage admin. Le plus simple et sûr : n'utiliser que `name_en` comme surcharge ? Non, asymétrique. Préférer une colonne `name_overridden boolean` (ou deux colonnes `custom_name_fr/en` nulles par défaut) posée par `update_service` quand l'admin renomme ; la synchro ne touche jamais ces colonnes.
3. Le nom fournisseur ne peut pas fuiter : `provider_name` n'est jamais lu pour le client, et seul l'admin (validé Zod, 1-200 car.) écrit la surcharge ; ajouter un test « aucun nom fournisseur dans le catalogue » avec un service renommé.
4. Alternative sans migration : la synchro ne réécrit pas `name_fr` s'il diffère du nom généré (comparaison), et le catalogue lit `name_fr`/`name_en` directement ; plus fragile, non recommandée.
